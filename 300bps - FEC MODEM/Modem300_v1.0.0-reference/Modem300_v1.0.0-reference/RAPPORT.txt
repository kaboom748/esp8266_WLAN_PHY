CONFIGURATION RETENUE
UART nominal 300 bauds, 8N1, binaire, sans RTS/CTS ni XON/XOFF.
Le diviseur UART suit la cadence mesuree du correspondant, avec une marge
de 80 us par caractere. Ce n'est pas une augmentation du debit utilisateur.
Radio FSK native +/-78125 Hz, 312500 echantillons/s, 2 echantillons/symbole.
A->B : canal 3 (2422 MHz). B->A : canal 11 (2462 MHz).
TDD : 4500 us par sens, cycle 9000 us. Une emission RF dure 1152 us.
Gain RF 0 / BB 0, accumulation IQ 64 : reglage du banc, pas une qualification
de portee. Capacite brute : un octet utilisateur par trame et par cycle.
RS(18,14), correction de deux octets codes, CRC32 independant apres FEC,
blanchiment PN9, numeros de sequence, sessions et suppression des doublons.
Calibration numerique de frequence sur les DEUX recepteurs a chaque trame
validee par CRC. Pas de suppression de cette calibration pour gagner du CPU.
Buffers de taille fixe, sans croissance de file pour masquer une congestion.

LOCALISATION DES ECHECS DANS CET ESSAI
UART : 6438 octets recus par A et 6432 par B, aucune erreur, aucun debordement,
aucun abandon d'entree ni de sortie. Intervalle d'observation maximal : 54 us.
A a sorti 6432 octets ; B en a sorti 6437. L'octet manquant est donc situe
dans le transport radio avant la sortie UART, pas perdu par le logiciel PC.
Radio A : 35 captures invalides, 12 sans synchronisation, 37 rejets FEC.
Radio B : 393 captures invalides, 149 sans synchronisation, 407 rejets FEC,

Calibration : 41070 validations sur A, 40720 sur B.
Ces compteurs ne permettent pas d'attribuer l'octet perdu a un candidat precis.

RETRIES ET DELAI
Quatre tentatives au maximum : initiale + trois retries. Jamais de cinquieme.
Essai ci-dessus : A = 6438/75/1/0, B = 6432/68/4/0 emissions aux rangs 1/2/3/4.
Les pertes d'ACK peuvent provoquer une expiration meme si l'octet est deja sorti.
L'essai artificiel split9_retry3, anterieur au dernier changement de service UART,
a rejete les trois premieres copies : le rang 4 a ete utilise 57 fois sur A et
60 fois sur B. Il teste la limite ARQ, pas le taux de perte naturel.
Avec un cycle de 9 ms, trois retries ne tiennent pas pour toutes les phases
d'arrivee. Si le temps manque, abandon a l'echeance, sans la repousser.

La borne demandee est 66,66 ms entre premiers bits sur les deux fils UART.
Elle N'EST PAS CERTIFIEE electriquement par ces essais USB/VM.
La cible logicielle est 29,833 ms apres l'horodatage FIFO reconstruit ; la limite
absolue reste 31,833 ms. L'age est arrondi vers le haut par pas de 125 us.
Retard maximal observe sur la cible : 86 us sur A, 152 us sur B.
Ce retard interne N'EST PAS une mesure de latence fil-a-fil.
Il faut une capture avec horloge commune des deux UART pour valider les 66,66 ms.

CAUSES ET CORRECTIONS ETABLIES
Le compteur de cycles CPU et micros() divergent pendant les changements de
canal : jusqu'a environ 60 us par operation mesuree. Les echeances UART utilisent
desormais micros(), sans changer le rythme d'echantillonnage RF.
L'attente avant emission masquait les interruptions sans servir l'UART ; elle
appelle maintenant le service UART. La gigue d'horodatage et de sortie a diminue.
La derniere correction n'est donc pas seulement un changement de canal radio.
L'origine physique des echecs RF restants n'est PAS identifiee : aucune preuve
ne permet de nommer Wi-Fi, Bluetooth ou Zigbee. Les essais de desactivation de
reconnexion et du timer de bruit SDK n'ont pas supprime les rafales observees.
La suppression experimentale du timer SDK n'est pas retenue dans le firmware.
Les silences TDD sont normaux et ne prouvent pas a eux seuls une perte de donnees.
